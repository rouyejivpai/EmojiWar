**S1/S2 实现期确立的口径（需回写设计文档）**

1. **修饰器判定用显式 `IsModifier`**，不能用 `!Self.IsIdentity`：普通投射物也带 `RechargeAdd`（自身充能代价），
   用"修正集非恒等"判定会把它误当修饰器，**覆盖掉前一个修饰器写下的耗蓝/延迟修正**。
2. **修饰器不作用于自己**：它自身的耗蓝按**已生效**的修正集结算；它写入的修正供**后续**物品使用，
   并占用"后续 N 个"的 1 层作用范围（作用范围在该物品处递减，耗尽即回恒等）。
3. **法杖基础施法延迟不被倍率放大**（§7.2 定稿口径 1 的严格化）：
   `间隔 = (物品自身延迟修正 + 修正集加值) × 修正集倍率 + 法杖BaseCastDelay`。
   （设计 §12.2 原文把基础延迟写成"物品延迟 + 基础延迟"的加值，未点明倍率只作用于物品延迟）
4. **序列倒转每槽位每次施法只生效一次**（`ReverseConsumed` 守卫），且主游标置 `-1` 哨兵、
   队列排空后直接结束本次发射。否则主游标会走回倒转符反复倒转 → 队列无限增长（被 Q7 截断但行为错误）。
5. **`RepeatNext` 已实现**：把游标之后的下一个非空物品额外排程 `(Operand−1)` 次（设计 §6.5 循环符文），
   同槽位重复触发受 Q7 单物品上限约束。
6. **dry-run 预估口径（P7）**：**耗蓝与实算必须逐项一致**（它是 Q2 中止判定与 S6 预览面板的前提）；
   序列时长按设计 §12.2 公式 `(N−1)×基础延迟 + Σ物品延迟`，与帧级时间线允许相差一个基础延迟（口径差异，已在自检里分别断言）。
7. **单体数值口径落表**（S1 内容已按此生成，设计 §12.5 的推论）：
   节能符文耗蓝由 **10 → 11**（否则设计 §12.4 样例① 口径算得 16 与表内不符）；
   急速咏唱 = 6/−0.05/+0.1、瞬发铭文 = 5/0/0.1、终止符 = 0/0/−0.05、快速充能 = 10/+0.1/−0.3。

### 0.2 S3 实现期确立的口径（2026-09-27）

1. **Buff 状态是两段式的**（这是 S3 的关键设计决定，D14/CastResolver 接线必须照此）：
   - **编译期快照**：buff 的"定义"（`CastBuffDef`：KeyHash/Stat/ValuePerStack/MaxStacks/Timing/Duration/StackRule/IsNegative）
     随 `LoadoutCompiler` 编进 `CastProgram`（`CastSpellData.AppliesBuff/Buff`），**已是现状**；
   - **运行期可变状态**（层数/剩余量/固化）必须放在 `CastRuntimeState` 里按槽位保存，并**入 `ComputeStateHash`**
     （执行文档 §4 + 流程 I-4 要求）。sim 侧**不能**直接持有 `ItemInstance`（那是表现/背包层的数据）。
2. **`BuffSet` 是值语义容器**（`BuffInstance[]` + `Count`，容量 8 = 结构常量）：每次修改都返回**新副本**（内部 `Clone`）。
   原因：`ItemTypes.cs` 文件头记载旧版事故就是"拷贝构造共享 buffs 引用导致委托逐发累积"。
   自检里三条"值语义"断言专门锁死这一点（改副本后原件层数/剩余量/条数均不变）。
3. **叠加规则（设计 §3.4）的落地口径**：
   | 规则 | 落地行为 |
   |---|---|
   | `Additive` | 同一实例 **+1 层**，剩余量刷新到不低于新时长；生效值 = 每层 × 层数 |
   | `Multiplicative` | 同上叠层；生效值 = 每层数值**迭代连乘**层数次（**不用 `Math.Pow`**，避免跨平台浮点差异） |
   | `Highest` | 只保留数值更大的那个，**层数固定 1**；后施加更小的值**不削弱**已有的 |
   | `RefreshTime` | **不增加层数**，只把剩余量刷满（自检里明确断言"层数仍为 1"） |
   | `Independent` | 不合并，**追加为独立条目**各自计时（同 Key 可并存多条） |
4. **递减时机按计时方式分离**（设计 §3.3）：`TickFrames` 只动时间型；`ConsumeTrigger(set, index)` 按**条**动次数型；
   `ConsumeCastAll` 动所有施法型。**次数型是按"哪一条被触发"递减**（所以签名带 index，而不是按 Key 模糊匹配）——
   否则 `Independent` 规则下"同 Key 多条"会被错误地只递减第一条。
5. **层数上限一律经 `ClampStacks`**（P11 配置驱动）：**三条路径都要过**——新建插入、Independent 插入、合并写回。
   只夹 `Stacks` 而不写回 `MaxStacks` 会留下"名义上限 > 生效上限"的脏状态（见 §0.3 坑#11）。
6. **引爆伤害来自配置**（`SpellSystemConfigSO.BuffDetonateDamagePerStack`，默认 5），已登记进 `Audit Numeric Config`；
   自检里专门断言"伤害口径随配置变化（7/层 → 21）"证明不是硬编码。
7. **修正运算顺序**（设计 §3.6 注）：`CastStatMod` 先写物品自身修正，再 `BuffRuntime.Accumulate` 叠加 buff 修正；
   加法型写 `XAdd`，乘法型写 `XMul`；最终值仍按 `(基础 + Add) × Mul`。自检断言 `(6+3+4)×0.5 = 6.5`。
8. **`BuffSet` 容量上限 8**：超出**静默拒绝**（不越界、不崩）；上层如需提示可自行判断 `Count == Capacity`。
9. **【已处理】`LoadoutCompiler` 的 buff 占位已拆除**（原 `LoadoutCompiler.cs` L140-164）：
   ```csharp
   // ---- buff 数值（第三层）：S3 上线前按"对本物品"并入 (a) ----
   float perStack = buff.ValuePerStack * (buff.MaxStacks > 0 ? buff.MaxStacks : 1);
   case BuffStat.ManaCost: self.ManaAdd += perStack; break;   // 同理 Delay/Recharge/Damage
   ```
   它把"该物品**施加**的 buff"按最大层数一次性折算进"物品**自己**"的数值，与设计 §3.1/§3.5 冲突
   （buff 是**附着在目标物品上的状态**，不是施加者的立即修正）。**S3 已删除该占位**，改为：
   触发时 `CastResolver.ApplyBuffEffect` 写进运行期 `CastRuntimeState.SlotBuffs[目标槽]`，
   再由 `EffectiveMods` 参与**目标物品**的结算。自检 `[SpellTest]` 里有一条专门的回归断言：
   "施加 buff 的物品自身耗蓝不受自身 buff 影响（占位时代会是 19，现在是 10）"。
   > ✅ **实测平衡影响**（拆占位改变了 2 个物品，其余 6 个不受影响）：
   > | 物品 | buff | 占位时代（错误语义） | 现在（设计语义） |
   > |---|---|---|---|
   > | `Spell_101 火花弹` | `buff_burn`：`Stat=Damage` / 每层 1 / 上限 5 / 次数型 2 次 / 加法，`Scope=Self` | 自己立刻 **+5 伤害**（1×5） | 每次触发给自己**叠 1 层**，伤害按层数成长（5→6→…→10） |
   > | `Spell_102 冰锥` | `buff_chill`：`Stat=Delay` / 每层 0.02 / 上限 3 / 次数型 3 次 / 加法，`Scope=Self` | 自己立刻 **+0.06s 延迟**（0.02×3） | 每次触发给自己叠层，延迟按层数增长 |
   > 两者的 `Scope` 都是 `Self` → 这正是设计意图"**buff 附着在物品卡实例上、跨施法保留**"（Q4/D14）。
   > 拆占位后 `Audit Spell Budget` 仍 **errors=0**（预算口径校验的是耗蓝/延迟/充能区间，伤害不在其中）。
   > 📌 **待平衡确认**：`buff_burn` 的 `Duration=2`（次数型）在每次施加时会把剩余量刷新到不低于 2，
   > 即"持续触发就不会掉层" → 火花弹伤害会单调爬升到 5 层上限。这是否符合预期需在 S1 内容调优阶段拍板。
10. **D14 的落点与 P5 的实现要点**（本轮实证）：
    - 加载在手上的法术卡，其 `ItemInstance` 的**真源是手部法术槽容器** `HandSpells_L/R`；
      法杖实例上的 `SpellSlots int[]` 只是 `SyncHandSpells` 写的**快照**（供 `LoadoutCompiler`/存档）。
      → 所以 buff 挂在"法术卡实例"上天然就随卡走。
    - `TryMove` 用 `e.Moving.WithCount(...)` 做**结构体拷贝** → buff 自动随拖拽移动（P5 成立，已断言）。
    - ⚠️ **唯一的泄漏点是"搬运既有物品"时用 `TryAdd(containerId, itemId, count)`**：它按 id+count **重建**实例，
      会丢掉 buff。`PushOverflow`（换杖裁槽挤回背包）原本正是这么写的 → 已改为新的
      `InventoryService.TryAddInstance(containerId, ItemInstance)`（保留整份实例）。
      **分工口径**：搬运既有物品用 `TryAddInstance`；凭空造新物品（购买/开局发放/奖励）才用 `TryAdd(id,count)`。
11. **槽位索引一律用"真实游标"，不要用 `spell.SlotIndex`**（S3 运行期发现的脆弱点，已修）：
    `CastSpellData.SlotIndex` 是"物品**自报**的槽位"，而待触发队列要靠 `program.SpellAt(slot)` 回查、
    buff 状态要靠 `state.BuffAt(slot)` 索引、单物品触发上限要按槽位计数 —— 一旦自报值与**数组位置**不一致，
    就会出现"延迟项被静默跳过 / buff 静默落空"这类**无声失效**（自检里真实踩到：`CastSelfTest.BuildSpell`
    用全局计数器当 SlotIndex，导致 4 条 S3 断言失败，而产品路径 `CompileSpell(card, table, slotIndex)` 是对的）。
    已改为：`ExecuteTriggers` 取 `int slot = state.Cursor` → 透传 `TriggerMainItem(..., slotIndex, ...)` →
    `EnqueueSlot / IncrementPerItem / SpendMana / ApplyEffect / ConsumeTriggerBuffs` 全部用它；
    `FireDuePending` 用队列里存的真实槽位。**新增任何按槽位索引的逻辑都必须照此办理。**
12. **📌 遗留（非阻断）：sim → 物品卡的 buff 回写尚未实现。**

### 0.4 S4 实现期确立的口径（2026-09-28）

1. **事件分两条路**（设计 §4.3 的 Q5 集合 = 5 个事件）：
   | 事件 | 产生处 | 送达被动的方式 |
   |---|---|---|
   | 施法开始 `CastStart` / 施法结束 `CastEnd` / 序列清空 `SequenceCleared` | `CastResolver` 内部 | **就地触发**（`FirePassives` 直接调用，不经总线） |
   | 命中 `Hit` / 击杀 `Kill` | `LockstepSimulation`（子弹 × 敌人） | 经 **`CastEventBus`** 转交（施法之外产生，必须解耦） |
   > 总线只为"施法流程之外产生的事件"服务。施法类事件绕总线没有意义（同帧同栈，反而多一层状态）。
2. **总线是实例、不是静态类**：回环/联机对拍会在**同一进程**跑两个模拟，静态队列会互相偷事件 → 非确定性。
   每台 `LockstepSimulation` 持有自己的 `CastEventBus`；消费时按 `SessionId` 过滤，同一会话内严格 **FIFO**。
   **不用 C# 委托事件**：多播顺序与订阅方数量不可控，两端一旦不一致即分叉。
3. **外部事件有固定 1 帧延迟**：`LockstepSimulation` 同一帧内**先施法、后跑子弹命中**，
   所以本帧命中产生的事件在**下一帧**被 `Tick` 末尾的 `DrainExternalEvents` 消费。
   这是确定性的（两端相同），但做"命中即时反馈"的表现层要注意这 1 帧。
4. **被动运行期状态放在 `CastRuntimeState`**（每手一份、按槽位）：
   `PassiveUsed[]`（本次发射次数，`BeginCast` 清零 → P6）+ `PassiveCooldown[]`（帧，逐帧递减、跨发射存活 → P6）
   + `PassiveDepth`（嵌套深度）。全部进 `ComputeStateHash`（执行文档 §4 明确要求）。
   > 📌 执行文档 §4 原表把"被动剩余次数/冷却"的宿主写成 `SimPlayer`；实际落在 `CastRuntimeState`（每手一份），
   > 同样满足"逐帧一致 + 入哈希"，且与 `SlotBuffs` 的槽位索引方式一致。**以本节为准。**
5. **嵌套语义（重要澄清）**：`FirePassives` 会把**所有监听同一事件的被动平级触发**（深度都在 0 层）——
   `PassiveDepth` **不会**因为"多个被动响应同一事件"而增长。
   嵌套只发生在**目标执行路径**上：被动/`TriggerItem` 的目标槽位若是**被动物品**，
   它会被作为嵌套被动**直接触发**（深度 +1，设计 §4.6 第 3 条）。上限 `MaxPassiveNesting` 来自配置（Q7）。
   → 自检里必须让"链上的被动"监听**不同事件**，否则测到的是"平级多响应"而非"嵌套"（本轮就踩过这个坑）。
6. **冷却至少 1 帧**：`CooldownFrames`/默认冷却为 0 时强制按 1 帧处理。
   否则 `WholeSequence` 类目标会立刻回头再触发自己（自递归）。
7. **资源模式 = 后扣 + 限次**（设计 §4.5）：蓝不够 → **跳过该被动**（`[passive] slotN skip: mana ...` 探针），
   不中止本次发射、不影响其它被动。
8. **目标执行口径（v1，📌 开放平衡项）**：
   - 目标物品被**重新执行一次效果**（`ApplyEffect` + 次数型 buff 递减）；
     **不推进主游标、不写修正集作用范围、不计入单物品触发上限** —— 它是"再触发"，不是主序列触发；
   - **只扣发起方的蓝**（被动扣 `Passive.ManaCost`），**目标物品不再单独扣蓝**；
   - `Self`/`SpecificItem` 按"跑该物品自己的效果"处理（不把自己再当被动触发一次，避免自递归）；
   - `TagGroup` 用被动自身的 `Condition.RequiredTags` 过滤（`None` = 匹配所有非被动物品）。
   > 📌 待拍板：目标"再触发"是否也应扣目标自身的蓝？（现在不扣 → 重放类被动偏强）
9. **被动默认不增加充能**（设计 §4.5）：靠**内容侧**把被动物品的 `RechargeAdd` 留 0 实现；
   若配了充能修正则照常结算；`Passive.IgnoreRecharge=true` 强制不增加（覆盖内容侧写法）。
10. **新增/改动的结构**：
    - 新 `Simulation/CastEventBus.cs`：`CastExternalEventKind`(Hit/Kill)、`CastExternalEvent`、`CastEventBus`（Publish/TryDequeueForSession/DropForSession/Clear/ToPassiveEvent）
    - `CastEventKind` += `PassiveFired = 7`（探针/计划事件用）
    - `SimBullet.Tags`（从 `CastShot.Tags` 带下来）→ 标签过滤型被动可用
    - `CastResolver.Tick` 增可选参 `CastEventBus bus = null, int ownerSession = 0`
    - `ApplyEffect` 新增 `SpellEffectKind.TriggerItem` 分支（按 `TargetScope/AffectCount` 执行目标，可形成嵌套）

## 3. 核心业务流程（端到端）

> 统一记法：`A → B` 表示 A 调用/触发 B；`[哈希]` 表示该状态必须进 `ComputeStateHash`；`[网络]` 表示涉及同步。

### 流程 A：启动与装备初始化
1. `ProcedureLaunch` → `DataComponent.Init()` → `ConfigService.Rebuild()`（校验 + 版本哈希）
2. → `ItemSystem.GrantStartingLoadout()`：左手学徒杖(3 槽) + 右手镜像长杖(5 槽)，各自预填出厂法术到**该手**法术槽
3. → `ItemSystem.Service` 建容器：`Backpack(30)` / `Hand_L` / `Hand_R` / `HandSpells_L` / `HandSpells_R`（`ActiveCapacity = 法杖槽数`，无法杖=0）/ `Shop(6)`
4. → 建房/开战时构造 `SimPlayerConfig` → `LoadoutCompiler.CompileHand(Hand_L/Hand_R)` → `Primary/SecondaryProgram` + `CastState`（魔力满、游标 0、延迟/充能 0）[哈希][网络]
- **边界**：手上没杖 → 程序 Empty → 该手不开火（Q：右手空手=无副武器）；法术槽 0 → UI 不生成格子（整块隐藏）

### 流程 B：装填 / 编辑序列（UI + 事务）
1. 打开背包（Tab，Popup 组不暂停）→ `BackpackForm.BindContainers()` 从 **QuickBind** 取全部引用
2. 拖拽法术卡：`UiSlotView.OnBeginDrag` → `UiDragManager.Begin`（幽灵=图标副本，保留抓取点）→ `UpdatePointer`（射线命中插槽优先 + 最近目标兜底）→ `End`
3. 落点判定与执行：`UiDropTarget.CanAccept` → `InventoryService.CanMove`（**同一套规则**）→ 通过则 `UiSlotView.OnDragCommitted` → `InventoryService.TryMove`
4. 事务结果：成功 → `SlotDirty` → `UiSlotContainer` 只刷新该格；失败 → 回弹 + Toast（`MoveReason` 文案）
5. 换杖裁槽：`InventoryService.ReconcileHand(hand)` → 新杖槽数 < 已有法术数 → 多余法术 `TryAdd(Backpack)`（放不下则**整笔拒绝换杖**）；其余法术**原地保留**（Q4/设计 §2.1）
- **边界**：法术每格 1 张不堆叠；跨手互拖允许；超出可用槽数 → `IndexInvalid`

### 流程 C：一次发射（正常，整序列 + 跨帧延迟）
1. 输入：左键=`FirePrimary`（左手序列）/右键=`FireSecondary`（右手序列）→ `S2CInputFrame` 同步 [网络]
2. `LockstepSimulation.Tick` → `CastResolver.Tick(program, ref state, dt, wantFire, plan)`
3. 前置：空杖（0 法术）→ 直接返回（不施法、不进冷却）；延迟/充能未走完 → 等待；回魔累加
4. **序列执行**：从游标 0 起逐物品
   - 立即类 → 生成效果（投射物/资源/序列操作）
   - 修饰器 → 写入"后续 N 个"的延迟/充能/耗蓝修正（按 item 修正 → buff 修正的顺序结算）
   - 条件门 → 判断下一个物品标签 → 触发或跳过
   - 循环/倒转 → 修改本次施法序列视图（临时）
   - 终止符 → 结束本次发射
   - 触发式/被动 → 不占主指针（由事件驱动）
5. **延迟结算（P2 新口径）**：**相邻触发间隔 = 该物品的施法延迟 + 法杖基础施法延迟**；间隔量化为帧（20Hz：0.05s = 1 帧）。间隔为 0 的物品同帧触发；间隔 > 0 时把待触发项写入 `PendingTrigger[]`（目标帧号 + 物品 + 修正快照），后续帧继续推进 [哈希]。序列跑完后进入充能（`RechargeTime`）
6. **产出**：`CastPlan`（多发 `CastShot`：伤害/弹速/寿命/穿刺/标签）→ `SpawnPlayerBullet` 落成 `SimBullet`
7. **收尾**：累计充能 = 基础充能 + Σ(已执行物品充能修正 × 充能倍率) → `RechargeRemaining`；清空临时修饰器/临时插入物品；游标回 0；发"施法结束"事件
- **上限**：总触发 ≤64 / 单物品 ≤8 / 被动嵌套 ≤3，超限截断并记探针

### 流程 D：法力不足中止（Q2/Q2b/Q2c）
1. 轮到某物品 → 结算该物品耗蓝（含修正）→ `state.Mana < cost`
2. → **立即终止本次发射**：该物品不生效、不扣蓝；**之前已执行的物品照常结算**（不可回退）
3. → 充能按**已执行物品累计**；→ 触发"施法结束"事件；→ 游标回 0
4. → 探针 `[cast] abort mana insufficient at slot=N`（便于自动化断言）

### 流程 E：Buff 生命周期
1. 施加：物品触发/条件满足/被动触发/资源换取 → `BuffRuntime.Apply(hostItem, buffDef)`
2. 叠层与计时：按叠加规则（加法/乘法/取最高/刷新时间/独立）更新层数；计时方式（时间/次数/施法次数，默认次数）
3. 生效：参与耗蓝/延迟/充能修正（顺序：物品自身 → buff）
4. 递减：触发一次/施法一次后递减；到期 → 移除 + 发"buff 消失"（Q5 集合内）
5. 交互：净化（移除负面）/转移（前→后）/增幅（+1 层）/固化（本次不递减）/引爆（每层 5 伤）
6. 宿主迁移：卡片在背包↔手↔法术槽之间移动时，buff **随卡**；**法术卡不可堆叠（P4 已定）**，故不存在"堆叠合并时 buff 归谁"的问题——若将来恢复可堆叠物品，口径为**合并后保留层数较高者的 buff，剩余次数取两者之和**，且必须计入哈希。
- [哈希]：层数 + 剩余次数

### 流程 F：被动触发
1. 事件源：`CastResolver`（施法开始/结束/序列清空）、`LockstepSimulation`（命中/击杀）→ `CastEventBus.Publish`
2. 订阅：每个 `SpellSO` 的 `PassiveEvent` 匹配 → 收集为本次事件的被动列表（**按序列顺序**）
3. 执行：用**临时指针**执行触发目标（后续 N/前 N/标签组/整个序列/自身），不改主指针
4. 资源：默认**后扣 + 限次**（`PassiveLimit` 每次施法次数）；冷却按帧
5. 嵌套：被动触发中再触发被动 → 深度 +1，>3 忽略
6. [哈希]：剩余触发次数 + 冷却

### 流程 G：命中 / 击杀事件链
1. `SimBullet` 命中敌人 → 结算伤害 → 发"命中"事件（携带：子弹 Id/标签/命中位置/目标）
2. 敌人死亡 → 发"击杀"事件（携带：击杀者/目标）
3. 事件 → 流程 F（被动触发）→ 可能再生成投射物/buff → 回到 1（受上限约束）
4. 表现层：只按 sim 的子弹与事件 Id 播特效（图标/音效不进 sim/网络）

### 流程 H：商店购买与装备
1. 波间商店（`ShopForm`）→ 购买物品卡（按钮买卖）→ `InventoryService.TryBuy`（钱够 + 背包放得下，整笔原子）→ 进背包
2. 装备：把背包里的法杖拖到 `Hand_L/Hand_R` → `TryEquipWand` → 裁槽/挤回（流程 B-5）
3. 新杖出厂装填：**P8 已定 = 不补**（换杖不按 `DefaultSpellIds` 补齐空槽，空槽即"少一段序列"）；`DefaultSpellIds` 仅用于**开局发放**（`StartingLoadoutSO`）。
4. 商店池：改为按 `ItemSO.Weight/Rarity` 确定性抽取（去掉 `Range(1,6)/(1,9)` 硬编码）

### 流程 I：联机同步（Host 权威）
1. Host：编辑 loadout → 编译两手 `CastProgram` + buff 快照 → `S2CLoadoutSync` 广播 [网络]
2. Client：`ApplyLoadout` 只读镜像（不自行编译，避免分叉）
3. 每帧：各端跑同一 `CastResolver` → 状态哈希逐帧对比（`S2CStateCheck`）
4. 哈希必须覆盖：两手魔力/延迟/充能/游标 + **延迟队列** + **buff 层数/剩余次数** + 被动限次/冷却
5. 波间编辑策略：Host 权威、开战锁定（已定）

### 流程 J：UI 交互
1. 背包：两手序列分列（左=主武器·左键 / 右=副武器·右键）；法术槽数随杖变化；无法杖=0 槽隐藏
2. 拖拽：背包↔法术槽、跨手、序列内排序；非法拖拽回弹 + 原因提示
3. 预览面板：调用 `LoadoutCompiler` 的 dry-run → 总耗蓝/总延迟/总充能 + 触发顺序（被动触发点标"可能触发"，不参与数值 [P7]）
4. HUD：两手各一行「法杖名 + 已装/槽数 + 下一发法术 + 魔力/充能」；**删除旧武器表的伤害/射速**
5. 配色：法杖=金橙、法术=蓝紫（已实现）

### 流程 K：配置体检与预算核算

### 7.1 由上述决策产生的连带改动（必须同步）

| 影响点 | 改动 |
|---|---|
| 数据模型（D1/D2） | `SpellSO` **移除 `Multicast`** 触发/效果分支；新增**法术卡不可堆叠**（`ItemSO.StackMax=1`，`Stackable` 标志去掉） |

### 7.2 已定稿（P2b = A：基础施法延迟口径）

| 选项 | 说明 | 结论 |
|---|---|---|
| **A** ✅ | **下调法杖基础施法延迟**（学徒 0.12s / 镜像 0.08s / 7 槽重杖 0.06s），保留"序列时长 ≤1.2s"的手感预算 | **已采纳**（基础延迟只作为"最小节奏"存在） |
| B | 保持现基础延迟（0.35/0.25），把序列时长预算放宽到 ≤2.0s、充能 0.8~1.6s | 放弃（周期 2.5~3.5s，偏"重炮"，与紧凑序列设计冲突） |
| C | 基础延迟改为"**下限**"而非加值（间隔 = max(物品延迟, 基础延迟)） | 放弃（与 P2 决策冲突） |

**定稿口径（D 交付物按此实现与校验）**
1. 相邻两物品的**执行间隔** = 前一物品的 `CastDelay` + 法杖 `BaseCastDelay`（同一序列内恒定叠加基础延迟）；
2. **序列时长**预算上限 **1.2s**，校验式 = `(物品数−1) × BaseCastDelay + Σ物品CastDelay`；
3. **一次发射周期** = 序列时长 + 总充能；总充能预算区间 **0.8~1.6s**；
4. 三个默认值全在 `WandSO`（配置），编码只写"缺失兜底"；
5. ✅ **连带收口（已采纳，落文案）**：样例③总充能原本 1.7s 略超上限 → `虚空回响` 充能修正 **+0.4 → +0.3**，样例③总充能 = **1.6s** 压线达标（设计文档 §12.4/§12.5 已回填）。
6. ✅ **实现侧硬要求**：`BaseCastDelay` 参与每次序列时长计算（不是"低于某值才生效"），充能与序列时长共同构成 `一次发射周期`；该周期用于 HUD 与预览面板的"预计循环时间"显示。

> 📌 **配置化之后，P2b 只是"默认值"选择**：数值一律进配置（见 §8），A 的数值作为出厂默认，后续在资产里随时可调即可。
