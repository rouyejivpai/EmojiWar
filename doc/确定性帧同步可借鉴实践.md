# 确定性帧同步：可借鉴实践清单

> 来源：从修仙时代（DreamRivakes2）FsBattle 战斗系统的架构与工程实践中提炼。
> 目标读者：准备做 1–4 人联机（合作 / 小规模 PvP）独立游戏的团队。
> 定位：**可移植的做法清单**，不是原项目的架构说明。原项目的完整分析见 `doc/AiCoding/战斗系统/` 下各页。

---

## 0. 一句话总结

值得抄的不是"帧同步算法"，而是**围绕确定性建立的一整套工程纪律**：逻辑与表现硬隔离、输入流录像、确定性打点与自动 diff、对象复用契约、同进程连续多局回归。

这几条大概覆盖了原项目 80% 的价值，工程量约为它的 5%。

---

## 1. 逻辑与表现硬隔离

### 做法

- 战斗/玩法逻辑是一个**独立模块**，不引用任何渲染、UI、输入 API，不持有 `GameObject` / `Transform`。
- 逻辑推进后，把这一帧发生的事情作为**事件批次**或**不可变快照**发布出去；表现层只消费，不反向查询逻辑状态。
- 表现层**不允许**在逻辑推进过程中读逻辑对象（哪怕同线程也不要，这是为了以后能拆线程留口子）。

### 为什么

- 逻辑可以脱离引擎单独跑 → 单元测试、Headless 批量回归、CI 全都成立。
- 表现随便改、随便重写，不会影响同步结果。
- 是后面所有条目的前提：没有这条，录像、确定性校验、追帧静默全都做不了。

### 关键约束

> **发布点必须在完整逻辑帧的边界上**，不能在帧中途发布"半成品"状态。
> 表现层拿到的必须是"某一帧结束时的状态"，否则一次卡顿导致的批量补帧会让画面撕裂。

原项目在视野系统上把这条做到极致：逻辑线程只在帧末安全点发布不可变快照，C# 复制后立刻释放指针，并且**明令禁止任何"同步查询逻辑层"的回退路径**——因为一旦留了这个后门，就一定会有人用，然后在多线程下崩溃。

---

## 2. 固定逻辑帧率，渲染帧率自由

### 做法

- 逻辑固定步长推进（4 人量级 **30Hz 足够**，追求手感可以 60Hz）。
- 渲染帧率不设限，表现层对位置/朝向做插值。
- 一帧渲染里可能推进 0 帧、1 帧或多帧逻辑，表现层必须能接受。

### 批量推进要用"时间预算"，不要用"帧数上限"

追帧（网络卡顿后补帧、断线重连）时需要一次跑多帧。控制方式：

```
while (队列里还有帧 && 已用时间 < 预算) {
    跑一个完整逻辑帧;   // 绝不在帧中途中断
    检查预算;           // 只在帧边界检查
}
```

- 正常态给小预算（原项目 4ms），追帧态给大预算（12ms），另加一个帧数上限兜底。
- **预算只能在完整逻辑帧结束后检查**。中途截断 = 破坏确定性，这是红线。
- 一个"重帧"可能超预算，这是可接受的；预算限制的是**连续占用**，不是单帧成本。

### 追帧期间静默表现

补 500 帧不要播 500 帧特效/音效。追帧时跳过表现事件消费，追完后**只回补一次终态**（血量、位置、状态图标等从当前逻辑状态直接拉取）。

> 这条要求表现层能"从逻辑状态重建自己"，而不是只能靠增量事件维持。设计 UI 时就要留这个能力。

## 3. 录像 = 初始状态 + 输入流

### 做法

- 每局开始时记录：随机种子、配置版本、参与者信息、初始状态。
- 之后只记录**每帧的输入**（谁在第几帧按了什么）。
- 重放 = 用同一初始状态重跑同一输入流。

### 为什么这是 ROI 最高的一件事

几乎零额外成本（数据你本来就要传），但白拿：

- **Bug 复现**：玩家一个几十 KB 的文件，你本地 100% 复现。
- **性能基线**：同一份录像反复跑，改动前后对比才有意义。
- **自动化回归**：CI 里跑一批录像，比对结果 hash。
- **不同步检测**：两端各跑一遍，diff。
- **玩家分享 / 观战 / 死亡回放**：顺带就有了。

### 注意

- 录像里要记**版本指纹**（代码版本 + 配置表版本）。版本不匹配的录像要能识别并拒绝，否则会浪费大量时间排查"假不同步"。
- 攒批下发的实现里，**尾帧容易丢**（不足一批留在缓冲区）。原项目就踩过：重放跑完录像却没到战斗结束条件。收尾时要强制 flush。

## 4. 确定性打点 + 自动 diff 工具

### 做法

在逻辑关键位置埋"一致性检查点"，每个点有稳定的 `CheckID` 和一小段数据，写入一个二进制文件：

```
CheckID | 数据长度 | 数据 | (逻辑帧号 | 帧内序号)
```

然后写一个 diff 工具，输入两份文件，输出**第一个有效分歧**。

### 为什么必须有工具

不同步 bug 靠肉眼和 log 是查不出来的。两次执行差了一个 bit，几百帧后表现为"技能没放出来"，中间隔着几万次状态变化。

一个几百行的 Python diff 工具能省掉几周时间。这是整套体系里性价比第二高的东西（第一是录像）。

### 检查点设计原则

**该埋的（常驻点）**：对象身份、创建、状态切换（暂停/恢复/停止）、销毁、随机数调用、帧号。低频、稳定、能串起对象生命周期。

**不该埋的**：
- `clear()` 之后恒为 0 的集合大小
- 每帧不变的常量
- **指针地址、未排序容器的遍历结果**（这些跨进程本身就不稳定，会产生假阳性）

**CheckID 唯一性要有机制保证**。原项目用一个"历史重复基线文件"卡住：只允许重复项减少，不允许新增冲突。

### 三层证据链（重要）

排查不同步时，强制区分：

| 层级 | 含义 | 能否定根因 |
|---|---|---|
| 状态注入点 | 首次持有不同的有效状态 | ✅ 根因候选 |
| 分支分歧点 | 该状态导致同一输入走不同分支 | 用于证明因果 |
| 可见症状点 | 下游表现不同 | ❌ 不能 |

**只看到症状层就去改症状层，是最常见的错误。** 必须往上追到状态注入点。

## 5. 对象复用契约

### 做法

任何进对象池的逻辑对象，必须满足：**复用后的状态等价于全新构造的对象**。

按字段列清单审查：

| 字段类型 | Init 要求 | 回收要求 |
|---|---|---|
| 基础状态 | 显式赋初值，不依赖构造默认值 | 可选防御性清理 |
| 容器 | 清空后再填充 | 清空以释放引用 |
| 引用/指针 | 重新绑定或置空 | 解除跨生命周期引用 |
| 定时器 / 回调 ID | 重建或重置 | 注销后清零 |

### 最小回归模式

```
1. 构造对象
2. 写入非默认的"污染值"
3. 回收
4. 重新取出并 Init
5. 与全新对象逐字段比较有效逻辑状态
```

### 为什么

原项目真实踩过：Buff 对象回池时残留了"暂停来源"集合，复用后行为不同 → 定时器一侧到期一侧不到期 → 整局不同步。

独立游戏更容易踩，因为往往一个进程连着打好几局，而测试时习惯性重启。

## 6. 同进程连续多局，必须进回归矩阵

### 做法

固定四组测试：

| 组 | 执行方式 | 排查范围 |
|---|---|---|
| A | 两个**新进程**分别跑同一录像 | 未初始化值、越界、容器顺序、平台差异 |
| B | **同一进程**连续跑同一录像多次 | 对象池、静态变量、退出清理 |
| C | 同一进程跑「录像 → 其他局 → 原录像」 | 跨局状态污染 |
| D | 固定 C，逐项改变量 | 缩小污染来源 |

### 关键认知

> **A 组稳定 ≠ B/C 组稳定。**
> "独立进程双跑一致"完全不能证明"同进程连打多局一致"。

对象池、静态变量、全局单例、延迟回调、异步退出流程，都可能跨局残留。独立游戏几乎必然是同进程连打，所以 B/C 组比 A 组更重要。

CI 建议分层：每次提交跑 A + 工具自测；每日跑 B/C。

## 7. 性能工程：用录像做基线

### 做法

- 在逻辑帧内部按子系统插入 zone 计时（编译开关控制，Release 默认关）。
- 用**固定录像**跑基线，产出每帧耗时、P50/P99/Max、各子系统占比。
- 优化前后跑同一份录像对比。

### 一条容易忽略但很关键的验证

> **打开 profiling 后，必须验证逻辑结果没变**（比如输出事件流的 MD5 一致）。

否则你测的是"另一个游戏"。原项目明确记录了这一步。

### 归因优先级

先测再改。原项目静态审计怀疑是玩法专属逻辑（搜打撤扫描、视野系统），实测发现平均耗时里**通用 Entity/Skill 框架占 89%**，玩法逻辑只占 0.3%。静态复杂度分析有价值，但不能替代运行时证据。

### 顺带的经验

- 关闭状态的调试 trace 也可能很贵：先构造字符串再进函数判断 `IsEnabled`，热路径上几千万次调用。**在调用点先判开关**。
- 尖峰（Max）容易受系统调度污染，优化收益应看 **Mean / P99** 和**可稳定复现的业务尖峰**。

## 8. 单一逻辑源

### 做法

联机双方（host / client，或客户端 / 服务器）跑的逻辑必须是**同一份代码 + 同一份配置数据**，不是"两份看起来一样的实现"。

### 推论

- 任何"客户端算一下，服务器也算一下"的逻辑都是不同步隐患。
- 会影响逻辑的输入（角色属性、模型尺寸、碰撞半径…）必须从**同一份数据源**读，不能一端读配置表另一端读运行时对象。

原项目为此把"战斗角色用哪个模型/性别"从 C# 委托回调改成 native 自己解析，就是因为跨语言的即时查询无法保证三端一致。

## 9. 纯 C# 实现确定性的注意事项

原项目用 C++ 写逻辑是为了绕开 Unity 的不确定性，但独立游戏用纯 C# 成本低得多。要注意：

**必须避免**：
- `float` / `double` 参与逻辑运算 → 用**定点数**（Q32.32 或 Q16.16）
- `Dictionary` / `HashSet` 的遍历顺序 → 用有序容器，或遍历前按稳定键排序
- `UnityEngine.Random`、`System.Random` 无种子 → 用自己实现的确定性 PRNG，状态进快照
- `object.GetHashCode()` / 引用地址参与逻辑判断
- `DateTime.Now` / `Time.deltaTime` 参与逻辑分支
- 多线程改逻辑状态
- `foreach` 遍历中依赖 GC 顺序或 finalizer
- LINQ 中的不稳定排序（`OrderBy` 是稳定的，`Array.Sort` 不是）

**排序必须全序**：任何排序的比较器都要有最终 tie-break（比如实体 ID），不能出现"两个元素比较相等但顺序不定"。

**建议**：把逻辑程序集单独拆出来，用 Roslyn Analyzer 或简单的编译期检查，禁止它引用 `UnityEngine` 和 `System.Random`。

## 10. 4 人游戏应该做的减配

以下是原项目有、但 1–4 人规模**不该照抄**的：

| 原项目做法 | 4 人游戏建议 |
|---|---|
| TCP/KCP/UDP/UNET 四套传输 + 多链路冗余 | 一套可靠 UDP（KCP / ENet / GameNetworkingSockets） |
| 客户端算 + 服务器录像重放审计 | **host 权威**（一名玩家跑逻辑）；真要 PvP 再上专用服 |
| 代码生成的全量状态快照（用于断线重连） | 掉线后**从头 replay 输入流追帧**，4 人局短，几秒就追完 |
| ACK 游标 / 重复 ACK 缺口补发 / 空帧压缩 | 每帧全量发，逻辑简单一个数量级 |
| C++ 逻辑 + C# 表现 + 代码生成 P/Invoke 桥接 | 纯 C# + 定点数学 |
| 服务器房间/资源线程调度模型 | 不需要 |

原项目那些复杂度全部是被 **24 人 × 30fps × 手游弱网 × 防作弊 × 跨语言** 这五个约束逼出来的。不背这些约束就不该背这些成本。

## 11. 落地顺序建议

如果从零开始，按这个顺序做，每一步都能立刻拿到收益：

1. **逻辑模块独立**（不引用引擎）+ 定点数学 + 确定性 PRNG
2. **固定 30Hz 逻辑帧**，渲染插值
3. **输入流录像**（录 + 放）→ 立刻拿到复现能力
4. **确定性 hash 打点 + diff 工具** → 立刻拿到不同步定位能力
5. **同进程连打多局回归**进 CI
6. **host 权威联机**：host 排帧下发，client 消费队列
7. **追帧 + 表现静默**（处理卡顿和重连）
8. 有余力再做：快照、观战、专用服

前 5 步是单机也能做、也该做的，做完之后加联机只是"多一个输入来源"。
