# 帧同步联机架构自查清单（给 AI Agent 执行）

## 0. 给 Agent 的执行说明

你要对当前 Unity 项目的多人联机战斗架构做一次**只读审查**，并输出一份审查报告。

**硬性约束：**
- 只读，不修改任何代码、资源或配置。发现问题只写进报告。
- 每条结论都必须给出证据：`文件路径:行号` 加上关键类名或方法名。找不到证据就标记为"无法判断"，不要推测后当成事实写。
- 已验证的事实和推断要分开写。推断必须标明"推断"。
- 跳过美术资源（模型、贴图、音频、特效）的内容分析。

**项目背景：**

| 项目 | 内容 |
|---|---|
| 引擎 | Unity，C# |
| 玩法 | 合作 PvE 动作战斗，2–4 人 |
| 网络 | Steam P2P / Steam 中继，没有专用服务器，房主是权威 |
| 同步 | 自研帧同步（lockstep），逻辑用定点数，设计目标是确定性 |
| 规模 | 同屏 30–200 个实体 |
| 命中判定 | 方案未定 |
| 审查目标 | 找出流畅度不足的架构性原因，同时评估确定性、性能和可扩展性 |

**目标架构（审查基准）：**

```
[输入采集] → 本地输入 ──发送──> [房主：按固定频率打包帧] ──广播──> 所有端（包括房主自己）
                                                                   │
                                                          [帧队列 / 抖动缓冲]
                                                                   │
                                           [确定性逻辑层：定点数，与引擎无关，固定 Tick]
                                                                   │ 每帧产出一批表现事件和状态
                                                          [事件队列 / 状态快照]
                                                                   │
                                   [表现层：Unity Update，插值/外推/本地预测，只读逻辑]
```

核心原则：**房主只是"打包帧的人"，它自己的输入也必须走同一条帧管线。所有端跑同一份确定性逻辑。表现层与逻辑层单向解耦。**

---

## 1. 第一阶段：摸清架构（先做，不评判）

先定位下面每一个环节，写出文件、类和方法。后面所有检查项都以这张表为基础。

| 环节 | 需要找到什么 |
|---|---|
| 输入采集 | 在哪里读取玩家输入、转成指令，是否量化（例如方向压缩成离散值） |
| 输入发送 | 非房主怎样把输入发给房主，走什么 Steam 通道（可靠/不可靠），多久发一次 |
| 帧打包 | 房主在哪里、以什么频率把各端输入合成一帧，缺少某人的输入时怎么处理 |
| 帧广播 | 帧的数据结构、序号、确认与重发机制 |
| 帧接收与排队 | 客户端怎样缓存收到的帧，什么时候取出执行 |
| 逻辑 Tick | 逻辑帧率是多少，由什么驱动（Update / FixedUpdate / 线程 / 累加器） |
| 逻辑层入口 | 世界、实体、系统的根对象在哪里 |
| 表现层 | 渲染对象怎样读取逻辑状态、怎样接收事件，怎样更新位置和动画 |
| 网络层 | 封装的是 Steamworks.NET、Facepunch.Steamworks，还是第三方传输层 |
| 碰撞/判定 | 命中、移动阻挡、范围筛选用什么实现 |
| 寻路 | 用 Unity NavMesh、A*，还是自研 |

把结果画成一张调用链图（Mermaid 或 ASCII）放在报告开头。

## 2. 第二阶段：逐项检查

每一项都要给出：**结论（符合 / 部分符合 / 不符合 / 无法判断）**、**证据**、**影响**、**建议**。

### A. 逻辑层隔离与确定性（优先级：最高）

确定性一旦被破坏，后面所有优化都没有意义。

- [ ] **A1 程序集隔离**：逻辑代码是否放在独立的 asmdef 里，并且不引用 `UnityEngine`？如果引用了，列出逻辑层里所有用到 `UnityEngine` 的地方。
- [ ] **A2 禁用浮点**：逻辑层中是否出现 `float`、`double`、`Mathf`、`Vector2/3`、`Quaternion`、`Time.deltaTime`、`Time.time`？定点数与浮点之间的互相转换是否只发生在"表现层读取逻辑状态"这一个方向？
- [ ] **A3 定点数学库**：乘除法的溢出与舍入规则是否统一？`Sqrt`、三角函数、`Atan2`、归一化是否用查表或整数算法实现，而不是先转 float 算再转回来？
- [ ] **A4 随机数**：逻辑层是否只使用一个由帧同步种子初始化的随机源？搜索 `UnityEngine.Random`、`System.Random`、`Guid.NewGuid`，确认它们没有出现在逻辑层。
- [ ] **A5 遍历顺序**：逻辑里是否遍历了 `Dictionary`、`HashSet`，或者按 `GetHashCode` 排序？这些顺序在不同机器、不同运行之间不保证一致。实体遍历必须按稳定 ID 排序。
- [ ] **A6 ID 分配**：实体、子弹、Buff 等对象的 ID 是否由逻辑层按确定规则递增分配？是否依赖 `GetInstanceID`、对象池的取出顺序或时间戳？
- [ ] **A7 外部依赖**：逻辑层是否读取了 `DateTime`、`Stopwatch`、系统时间、帧率、屏幕尺寸、本地设置？是否用了多线程、`async`、`Task`、协程并在其中修改逻辑状态？
- [ ] **A8 静态可变状态**：逻辑层中是否存在跨局残留的 `static` 可变字段？重开一局时是否会被完整重置？
- [ ] **A9 表现层反向写入**：表现层（MonoBehaviour、动画事件、`OnTriggerEnter`、`OnCollisionEnter`、Animator 的 RootMotion）是否会直接修改逻辑状态？**任何表现层到逻辑层的写入都算严重违规**，必须改成"生成输入指令，进入帧管线"。
- [ ] **A10 配置数据**：逻辑层读取的配置表或 ScriptableObject 中是否含有 float 字段？加载时是否转换成定点数？各端的配置版本是否一致（开局时有没有校验配置哈希）？

搜索提示（逻辑层目录内）：
```
float |double |Mathf\.|Vector[23]|Quaternion|Time\.(deltaTime|time|fixedDeltaTime)
UnityEngine\.Random|System\.Random|Guid\.NewGuid|DateTime|Stopwatch
Physics\.|Physics2D\.|Rigidbody|Collider|OnTrigger|OnCollision
foreach.*(Dictionary|HashSet)|\.GetHashCode\(|GetInstanceID
Task\.|async |Thread|Parallel|StartCoroutine
static (?!readonly|const)
```

### B. 不同步检测与可复现（优先级：最高）

- [ ] **B1 状态哈希**：是否每 N 个逻辑帧对关键状态（位置、血量、随机数状态、实体数量）计算一次哈希，并在各端之间比对？
- [ ] **B2 分叉定位**：发现不同步后，能否导出双方同一帧的完整状态以便比对，而不是只报一个"不同步"？
- [ ] **B3 输入录制**：是否记录每一局的种子、初始数据和全部输入帧？
- [ ] **B4 无头回放**：能否在不启动渲染的情况下，用录制的输入把一局重放一遍（EditMode 测试或命令行），并且两次重放得到相同的最终哈希？**这是验证确定性最有效的自动化手段。**
- [ ] **B5 跨平台/跨构建**：Mono 与 IL2CPP、Debug 与 Release、不同 CPU 之间，同一段录像的哈希是否一致？有没有做过验证？

### C. 帧同步管线（优先级：高）

- [ ] **C1 房主输入公平性**：房主自己的输入是否也经过"采集 → 打包 → 执行"的同一条管线？还是房主直接在本地生效？后者会造成房主零延迟、其他人有延迟，并且房主的执行时序可能与其他端不同。
- [ ] **C2 打包频率**：房主打包帧的时钟由什么驱动？是否受房主自身渲染帧率影响？房主卡顿时是否会导致所有人一起卡？（理想情况是用独立的计时累加器按固定间隔打包，与渲染帧率无关。）
- [ ] **C3 输入缺失**：某个客户端的输入没能按时到达时，房主是一直等待（整局一起卡住），还是沿用它上一帧的输入或填空输入后继续推进？
- [ ] **C4 传输可靠性**：输入和帧走的是可靠通道还是不可靠通道？
  - 如果走可靠有序通道，丢包时会出现队头阻塞，表现为周期性卡顿。
  - 如果走不可靠通道，是否在每个包里冗余携带最近几帧的输入或帧（冗余发送），并配合 ACK 与重发？
- [ ] **C5 Steam 发送参数**：检查 `SendP2PPacket` / `SteamNetworkingSockets` / `SteamNetworkingMessages` 的发送标志（例如是否启用了 NoNagle / NoDelay），以及每帧是否及时调用接收和 Flush。
- [ ] **C6 包体大小**：一帧的字节数是多少？空帧是否做了合并或压缩？输入是否量化成少量比特？
- [ ] **C7 帧序号**：帧序号是否连续？乱序、重复、跳号时是否都有处理？

### D. 本地操作手感（优先级：高，最可能是流畅度问题的根源）

- [ ] **D1 实测延迟**：计算非房主从按下按键到画面产生反应需要多少帧和多少毫秒（估算公式：采集等待 + 上行 + 房主打包等待 + 下行 + 抖动缓冲 + 表现延迟）。房主又需要多少？把两者的差值写进报告。
- [ ] **D2 输入延迟策略**：是否有统一的输入延迟（例如所有人都延后 2–3 帧执行）？这个值是固定的，还是根据 RTT 动态调整？
- [ ] **D3 表现层预测**：本地玩家按键后，表现层是否立刻给出反馈（起手动画、转向、移动、音效），而不是等权威帧回来？权威帧到达后，表现层怎样平滑地纠正到权威位置？
- [ ] **D4 回滚可行性评估**（只评估，不要求已经实现）：
  - 逻辑状态能否完整拷贝或序列化成快照？一次快照需要多少耗时和内存？
  - 单个逻辑帧的耗时乘以可能需要重算的帧数（例如 RTT 150ms 在 30Hz 下约 5 帧），是否在帧预算以内？
  - 表现事件能否在回滚时撤销或去重（例如命中特效不能重复播放）？
  - 根据以上几点，给出"表现层预测 / 输入延迟 / 完整回滚"三种方案中推荐哪一种，并说明理由。

### E. 帧消费与抖动缓冲（优先级：高）

- [ ] **E1 消费时机**：客户端收到帧后是立刻执行，还是按本地时间轴均匀地执行？经过 Steam 中继时帧的到达间隔并不均匀，如果收到就执行，逻辑推进就会忽快忽慢，画面随之抖动。
- [ ] **E2 缓冲深度**：是否维护一个目标缓冲深度（例如 1–3 帧）？缓冲过多时是否轻微加速消费，过少时是否轻微减速，而不是突然跳帧？
- [ ] **E3 追帧预算**：大幅落后时（例如切到后台后返回、网络卡了一下），是否限制每次 `Update` 最多执行几帧、最多花几毫秒，而不是一次把全部落后的帧跑完、造成长时间卡顿？
- [ ] **E4 追帧期间的表现**：追帧期间是否屏蔽或合并表现事件（不重复播放大量特效和音效），追完后再按最终状态统一刷新一次表现？

### F. 逻辑与表现分离（优先级：中高）

- [ ] **F1 数据通道**：逻辑层怎样通知表现层？理想做法有两种：一是每个逻辑帧结束后，把这一帧的表现事件作为一批放进队列，由表现层在 `Update` 中取出处理；二是表现层读取逻辑层发布的只读状态。表现层不应在逻辑帧执行到一半时读取逻辑状态。
- [ ] **F2 位置平滑**：渲染对象的位置是直接设置成逻辑位置（在逻辑帧率低于渲染帧率时会一顿一顿），还是在上一帧与当前帧的逻辑位置之间插值，或者按速度外推？
  - 插值：多约一个逻辑帧的延迟，但完全不抖，适合远端玩家和怪物。
  - 外推：没有额外延迟，但转向或停止时会冲过头，需要纠正。
- [ ] **F3 渲染与逻辑解耦**：渲染帧率是否与逻辑帧率无关？逻辑是否跑在 `FixedUpdate` 中，并受 `Time.fixedDeltaTime` 与 `Maximum Allowed Timestep` 的影响（这可能引发"死亡螺旋"或逻辑时间漂移）？
- [ ] **F4 动画驱动**：动画状态是否由逻辑状态驱动（技能 ID + 已进行帧数 → 动画的播放时间点）？启用 RootMotion 时，位移是否由逻辑层决定，而不是由动画决定？
- [ ] **F5 表现层的量**：特效、飘字、音效是否纯属表现、不回写逻辑？远端单位的表现更新能否被裁剪（例如不在屏幕内时不更新）？

### G. 物理、判定与寻路（优先级：中高，当前方案未定，重点给出建议）

- [ ] **G1 Unity 物理**：战斗判定（命中、阻挡、范围筛选）是否依赖 `Physics`、`Physics2D`、`Rigidbody`、`OnTrigger`？如果依赖，属于确定性风险（PhysX 和 Box2D 的 Unity 版本都使用浮点运算，不保证跨机器一致，也不支持快照与回滚），并且需要迁移。
- [ ] **G2 维度判断**：战斗能否简化为俯视平面的 2D 逻辑，只把高度留给表现层？如果可以，推荐使用定点数 2D 碰撞：圆、胶囊、凸多边形、扇形，外加一个宽相位网格。
- [ ] **G3 宽相位**：碰撞和范围查询是否有空间划分（均匀网格或四叉树）？在 200 个实体时是否存在 O(n²) 的全量两两检测？
- [ ] **G4 寻路**：寻路是否放在逻辑层并使用定点数？如果用的是 Unity NavMesh，同样是浮点，只能用于表现层。AI 寻路是否做了限频（例如每隔 N 帧才重新寻路一次、目标变化不大时复用路径）？
- [ ] **G5 Unity Collider 的用途**：Collider 是否只用于表现层用途（镜头遮挡、脚底贴地、点击拾取）？

### H. 性能（优先级：中）

- [ ] **H1 逻辑帧耗时**：是否有 Profiler 标记（`ProfilerMarker`）统计单个逻辑帧的耗时？在 200 个实体、4 个人的压力场景下，耗时的平均值和 P99 是多少？（参考：逻辑帧耗时应远小于逻辑帧间隔。如果打算做回滚，还需要能在一个渲染帧内重算好几帧。）
- [ ] **H2 GC 分配**：逻辑 Tick 和表现更新中是否有每帧的托管内存分配（LINQ、闭包、装箱、`new List`、字符串拼接、`foreach` 遍历接口类型）？是否用了对象池？
- [ ] **H3 房主负载**：房主同时承担渲染、逻辑、打包和网络。房主的逻辑和网络处理是否可能被渲染卡顿拖累？是否考虑过把逻辑放到独立线程（前提是表现层只读取已发布的快照）？
- [ ] **H4 热点**：列出逻辑帧中耗时最高的 5 个系统（AI、寻路、碰撞、Buff、技能筛选），并给出优化方向，例如分帧执行、限频、空间划分、缓存。
- [ ] **H5 网络线程**：Steam 回调和收包是否在主线程上处理？主线程卡顿时是否会导致收包延迟？

### I. 断线、中途加入与房主迁移（优先级：中低）

- [ ] **I1 断线重连**：客户端断线后能否重新加入？是依靠房主保存的全部输入帧从头追帧，还是依靠状态快照？
- [ ] **I2 中途加入**：新玩家能否在对局中途加入？这需要完整的状态快照，外加快照之后的输入帧。
- [ ] **I3 房主迁移**：房主掉线后，由于每个客户端都持有完整的逻辑状态，理论上任何客户端都可以接任打包帧。当前实现是直接结束这一局，还是支持迁移？迁移时怎样对齐帧序号、处理未确认的输入？
- [ ] **I4 快照完整性**：如果有快照，是否覆盖了随机数状态、ID 分配器、计时器队列、碰撞和寻路的缓存（需要保存或按确定规则重建）？

### J. 调试与验证工具（优先级：中）

- [ ] **J1 网络模拟**：能否模拟延迟、抖动和丢包（Steam 的调试模拟参数，或者自己写一层 Transport 包装）？是否在 150ms RTT、30ms 抖动、5% 丢包的条件下测试过？
- [ ] **J2 单机多开**：能否在一台机器上开多个实例互相联机测试？
- [ ] **J3 调试可视化**：能否把逻辑层的碰撞体、判定范围和寻路路径画在画面上，与表现层的模型对比？
- [ ] **J4 网络统计 HUD**：能否实时显示 RTT、缓冲深度、输入延迟帧数、追帧状态、逻辑帧耗时和不同步告警？

## 4. 参考指标（用于判断"是否达标"）

| 逻辑帧率 | 20–30Hz 适合技能类战斗；动作类建议 30Hz 或更高 |
| 本地操作到画面反馈 | 表现层给出反馈：≤ 1 个渲染帧；逻辑确认：≤ 100ms（在 RTT 60ms 左右时） |
| 房主与非房主的操作延迟差 | 尽量为 0（房主也走帧管线，或者统一输入延迟） |
| 抖动缓冲深度 | 1–3 帧，并且能动态调整 |
| 单个逻辑帧耗时（200 实体） | 小于逻辑帧间隔的 20%；如果要做回滚，需要更低 |
| 逻辑 Tick 的 GC 分配 | 0 B/帧 |
| 不同步 | 同一段录像多次无头回放，哈希完全一致 |
