# EmojiWar2 流程状态机定义（GameFramework 规范）

> 依据：EllanJiang GameFramework（StarForce 范式）——流程继承 `ProcedureBase`，
> 通过 `ProcedureComponent` 的 `m_AvailableProcedureTypeNames`（类型名数组）注册，
> `m_EntranceProcedureTypeName` 指定入口，运行时反射创建，`ChangeState<T>()` 驱动切换。
>
> 代码单一来源：`Assets/GameMain/Scripts/Procedure/ProcedureTypes.cs`
> （改流程先改它；场景 YAML 与 Builder 均引用该常量，避免漂移）。
> 更新时间：2026-08-28
>
> 2026-09-04 更新：主界面四按钮（单人游戏[占位]/多人游戏/设置/退出游戏）；
> 新增「多人游戏中转」与「局域网房间列表」流程：
>   Menu ─多人游戏→ ProcedureMultiplayer（MultiplayerForm：玩家名 + 创建房间/加入游戏）
>     ├ 创建房间 → StartHost+本机加入 → ProcedureRoom（直进房间，跳过旧大厅）
>     └ 加入游戏 → ProcedureJoinRoom（JoinListForm：RoomDiscovery UDP 发现房间列表
>        + 刷新按钮；点房间项 → TCP 连房主 → ProcedureRoom）
> 旧 ProcedureLobby/LobbyForm 保留为 AutoPlay 回归捷径（TriggerStartGame 直达），
> 新 UI 不再经它；从房间「离开/解散」返回 ProcedureMultiplayer。
> 房间发现协议见 RoomDiscovery.cs（Host 房间阶段应答 EWSCAN；Client 广播扫描收集）。

## 2. 状态与转换表

| 状态 | 职责 | 进入（来源） | 离开（去向/触发） |
|---|---|---|---|
| **Launch** | 资源初始化（构建版 `ResourceComponent.InitResources`）、加载数据表 | 启动（入口） | → Menu：资源/数据表就绪后自动 |
| **Menu** | 主菜单 UI（标题/开始按钮） | Launch | → CharacterSelect：点击"开始游戏" |
| **CharacterSelect** | 角色选择 UI（4 角色），写入 `SelectedCharacterId` | Menu | → Lobby：选择角色后 |
| **Lobby** | 大厅 UI（玩家名/IP、创建/加入/返回） | CharacterSelect / GameOver返回菜单 / Room离开 | → Room：创建（Host 模式）或加入（Client 模式）；→ Menu：返回 |
| **Room** | 联机房间 UI（玩家列表/准备/离开），全部准备自动开始 | Lobby / GameOver返回房间 | → Battle：全部玩家准备（Host 广播 `S2CBattleStart`）；→ Lobby：离开/解散/房主退出 |
| **Battle** | 战斗（确定性帧同步模拟 + SimView 渲染），波间商店 UI（Battle 内联打开 ShopForm） | Room | → GameOver：模拟战斗结束（全部玩家死亡，`OnBattleEnded`） |
| **GameOver** | 结算 UI（重新开始/返回菜单） | Battle | → Room：返回房间（Host `ResetRoom` 重置，准备下一局）；→ Menu：返回菜单（解散房间，全员回大厅） |

### 关键守卫条件

- **全部准备才开战**：`NetHostLogic.HandleReadyChange` 检测 `AllReady()`（≥1 人且全部 `Ready=true`）→ 广播 `S2CBattleStart{Seed}` → 各端 `InitializeSimulation(seed)` 重建确定性模拟。
- **Battle 防重复进入**：`ProcedureBattle` 用会话级静态标志 `s_BattleSession`——一局内重复 `ChangeState<Battle>` 直接忽略（防重复开局/场景叠加），玩家死亡进结算或返回菜单才复位。
- **结算后回房**：GameOver"返回房间"→ Host `ResetRoom()`（`ReplayRecorder.End`/`DeterminismTracer.End`、清敌、准备复位、seed=0 房间模拟）→ 全员回 Room 准备下一局。
- **房主退出**：`NetServer` 断开 → Host 广播 `S2CRoomClosed` → 客户端 `RoomClosed()` → 返回 Lobby。

## 6. 状态机 ↔ UI 互动定义表（2026-08-28）

> 互动总原则（GF 规范）：
> - **流程 → UI**：`GameEntry.UI.OpenUIForm(资产路径, UIGroup, userData)`（打开）/ `CloseUIForm`（关闭），UI 生命周期归框架管；
> - **UI → 流程**：UIForm 上的**静态事件类**触发（`XxxEvents.RequestXxx()`），流程在 `OnEnter` 订阅、`OnLeave` 退订；
> - **网络 → UI**：`RoomEvents` 事件中心（网络层触发，UI/流程订阅，解耦）；
> - **模拟 → UI**：UI 以**只读轮询**方式从 `GameEntry.SimView`（确定性模拟表现层）读数据（HUD/商店），不反向影响逻辑。

- **UI 不直接碰逻辑**：HUD/商店通过 `GameEntry.SimView` 只读快照；所有状态变更（准备/购买/离开）都经事件 → 流程 → 网络/模拟，符合"UI 只响应数据变化"原则。

## 7. UI 开发约定：动态列表预留占位子物体（2026-09-01）

> 约定来源：`CharacterDockForm` 角色卡片列表（运行时按 JSON 动态实例化）。
> 目的：在编辑器中直接观察预制体的父子级关系，而非运行时才生成。

### 规则

**任何运行时动态生成一组子物体的 UI 容器（列表/网格/条目池），预制体里必须在挂载位置预留一个占位子物体**——即使它一定会在运行时首先被清空。

### 命名与实现

| 项 | 约定 |
|---|---|
| 容器命名 | 语义化容器名（如 `CardContainer` / `ItemList` / `SlotGrid`） |
| 占位子物体命名 | `Xxx_Template`（如 `Card_Template`），挂与运行时条目**相同的组件结构**（组件 + 子物体），便于在编辑器查看布局 |
| 运行时清理 | 动态生成逻辑**先清空容器全部子物体**（含占位），再按数据实例化真实条目 |
| 典型做法 | Builder 用代码创建占位（避免 prefab 实例化依赖）；运行时 `Destroy` 全部子物体后重建 |

### 示例（CharacterDockForm）

```
panel_PanelSlide
└── CardContainer（运行时清空后按 character_select.json 实例化）
    └── Card_Template（占位：CharacterCard 组件 + Highlight/Icon/Name/Stats）
```

- Builder：`RoomSetupBuilder.CreateCharacterDockFormPrefab` 用代码建 `Card_Template`
- 运行时：`CharacterDockForm.BuildCards` 先 `Destroy` 容器全部子物体，再 `Instantiate` 真实卡片

## 8. 帧同步定期状态对账（2026-09-02）

> 背景：构建版偶发"双方实体位置/敌人/波次逐渐不一致"。排查确认原架构是**纯确定性信任**：
> Host 每 tick 广播 `S2CInputFrame`，双端各自 `Simulation.Tick()`，**运行期零校验**——
> 一旦输入序列或 tick 节奏出现一次分歧，模拟永久漂移且无人察觉。

### 已加的防线

| 层 | 机制 | 位置 |
|---|---|---|
| 1. 帧号守卫 | 客户端收到 InputFrame 校验 `frame.FrameIndex`：`<= 本地` 丢弃（防重复推进）；`> 本地+1` 且战斗中 → 探针告警"跳号" | `NetClientLogic.HandleInputFrame` |
| 2. 定期状态对账 | Host 每 20 tick（1 秒）广播 `S2CStateCheck { FrameIndex, StateHash }` | `NetHostLogic.HostTick` |
| 3. 确定性状态哈希 | `LockstepSimulation.ComputeStateHash()`：FNV-1a over 帧号/波次/商店标志 + 玩家/敌人/子弹（ID、位模式位置、HP、弹药） | `LockstepSimulation` |
| 4. 客户端哈希环 | 每 tick 记录 `(FrameIndex, Hash)` 到 256 槽环形缓冲；收到 StateCheck 按帧号回查对比，不等 → `不同步! frame=.. host=.. local=..` 探针 + LogError | `NetClientLogic`（`RecordFrameHash`/`TryVerifyFrame`） |

### 关键设计要点

- **只战斗阶段对账**：房间阶段各端玩家加入（S2CSpawnEntity）时序不同，哈希天然不等，不是不同步。门控：Host 侧 `m_BattleStartBroadcasted`；客户端 `Simulation.Seed != 0`。
- **哈希只含"影响推进的确定性状态"**：SessionId / 子弹 OwnerSession 是纯元数据（Host 传真实 session，Client 一律 -1，不参与任何 Tick 决策）——混入会**恒误报**（实测 frame 1 起全不等，剔除后全一致）。
- **客户端哈希环而非即时对比**：TCP 合帧送达时 StateCheck(N) 到达时本地可能已 tick 到 N+k，无法即时算 N 帧哈希 → 每 tick 记环、按帧号回查。
- 校验**不自动修复**（用户选择 1 层）：检测到不同步仅告警，排查用既有 trace/重放工具定位。

### 附带修复：NetServer 广播崩溃（真实不同步诱因之一）

`NetServer.Poll()` 的 foreach 与 `Broadcast()` **共用 `m_SessionList`**：Poll 遍历 session 处理消息时，消息回调（HandleJoin/HandleReadyChange）内广播会 `Clear()`+`AddRange()` 正在被枚举的列表 → `InvalidOperationException: Collection was modified`，双实例联机必现崩溃/流程中断。修复：`Broadcast()` 改用独立 `m_BroadcastList`。

### 验证

双实例构建版（`-autocreate -autoready` + `-autojoin -autoready`）跑 200+ 帧：
- 修复前：`Collection was modified` 崩溃；哈希含 SessionId 时 frame 1 起全报"不同步"（误报）
- 修复后：稳定运行，客户端 12 次对账**全部一致**（frame 41→221），0 不同步；双端位置逐帧吻合

## 9. Bug 实录：非主机点角色卡片被踢回大厅（2026-09-02）

> 现象（必现）：Client 加入房间后点角色卡片，连接立即断开并**弹回大厅界面**；
> Host 点卡片正常。初看像"UI 错误打开房间"，实为**网络解码崩溃导致断线**。

### 根因（两层）

**① MsgId 冲突 → 反序列化越界 → session 崩溃（主因）**

`C2SChangeCharacter` 与 `S2CChangeCharacter` 共用 `MsgId.ChangeCharacter = 1104`
（注释"按方向区分"），但 `NetCodec` 用**单字典**注册工厂：
`Register<C2SChangeCharacter>()` 先注册 1104 → `Register<S2CChangeCharacter>()` 后注册**覆盖**。
Host 收到 Client 的 C2S 帧（payload=4B CharacterId）后按 **S2C 工厂**创建实例反序列化
（读 8B EntityId+CharacterId）→ `BinaryReader` 越界 →
`NetServerSession.Poll failed: Unable to read beyond the end of the stream` → 该 session 断开 →
Client `OnModeChanged->Offline` → `RoomClosed` → 回大厅（LobbyForm 弹出 = 用户看到的"房间 UI"）。
Host 点卡片走本地 `SetLocalCharacter`（不经网络编码），故无此问题——与"仅非主机必现"吻合。

**② 回包回环（次因，同改修）**

即使不断线，Client 收到**自己发起**的 S2CChangeCharacter 回包（`EntityId == m_MyEntityId`）
后原代码再次 `CharacterDockEvents.Change` → `ProcedureRoom.OnCharacterChanged` 再次上行 →
Host 再广播 → **无限回环**（消息风暴 + 高频探针 I/O）。

### 修复

| 文件 | 改动 |
|---|---|
| `NetProtocol.cs` | `ChangeCharacterReq = 1105`（C2S 独立 ID）；`ChangeCharacter = 1104` 仅留 S2C |
| `NetMessages.cs` | `C2SChangeCharacter.Id` → `MsgId.ChangeCharacterReq` |
| `NetHostLogic.cs` | 收 C2S 的 case 改 `MsgId.ChangeCharacterReq` |
| `NetClientLogic.cs` | 收到自己回包（`EntityId == m_MyEntityId`）只同步 `SelectedCharacterId`，**不再触发 `CharacterDockEvents.Change`**（UI 在点卡时已刷；触发会再次上行） |
| `AutoPlay.cs` | 新增 `-autocard` 复现开关（进房间后自动点第 2 张卡，观测 ChangeCount/UIForms/断线） |
| `CharacterDockForm.cs` | 加 `ChangeCount` 计数 + `CardCount`/`SimulateCardClick` 供自动复现 |

### 经验教训（协议层）

**C2S 与 S2C 消息绝不能共用同一 MsgId**——`NetCodec` 工厂按 ID 单字典注册，
同 ID 必然被后注册方向覆盖，导致对端用错消息类型反序列化（payload 长度不符 → 越界 → 断线）。
若需双向语义，拆两个 ID 或显式按方向分字典。

### 方案（UI 组分层）

| UI 组 | Depth | 内容 |
|---|---|---|
| `Default` | 0 | 各流程主窗体（Menu/Multiplayer/Lobby 等） |
| `Popup` | 0 | 角色抽屉 `CharacterDockForm`（全屏滑出，与房间条异组共存） |

- 同一 UI 组内后开的窗体使先开的 Pause/`SetActive(false)`——房间条必须与 Dock **异组**，

  也不会把任何其它窗体置为不活动（互不影响）。
- 组可在运行时动态注册：`AddUIGroup("Top", 100)` 后 `OpenUIForm(..., UIGroup.Top, ...)`。
- 视觉互不干扰：Dock 全屏面板展开时位于 RoomForm 右缘 420px 悬浮条之下，
  Dock 顶部"确认选择"按钮运行时左移到 `(300,320)`（屏幕 x≈1260 < 1500），避开房间条遮挡区。

## 12. 选角面板响应式/自适应（2026-09-09）

### 现状机制（改造前）

- 参考分辨率 1920×1080、`ScaleWithScreenSize`、`MatchWidth=0`（**按屏幕宽度等比缩放**）：
  横向画布恒为 1920 参考宽；**纵向可视参考高 = 屏高×1920/屏宽**——超宽屏(<16:9 比例关系)时
  可视高度 <1080，超窄/高屏时 >1080。
- 收起：`SidePanelForm` 用 DOTween 把滑动主体从 `(0,0)` 移到 `(rect.width+30,0)`——**位移量按
  面板当前实际宽度动态计算**（这块本来自适应）；右缘 64px Tab 常驻根上，收起后仍可点。
- 不足：滑动主体原为"固定 1920 宽、锚右缘"；顶部控件（标题/收起/确认）用**中心+460 绝对定位**，
  异宽高比（尤其超宽屏）下会被裁出可视区；卡片列手写 `index*200` 定位，无布局组/滚动。

### 改造（方案A：仅 Dock，运行时布局，不改预制体）

| 项 | 做法 |
|---|---|
| 滑动主体 | 运行时锚改为 `(0,0)-(1,1)` 全父拉伸、offset=0 → 任意宽高比都铺满（收起位移仍按实际宽动态算，无需改） |
| 顶部控件 | 标题/收起/确认 统一重锚为**贴顶边**（anchor y=1、pivot 顶部），规范偏移：标题 x=-260 距顶80、收起 x=300 距顶80、确认 x=300 距顶220（保持在房间条左侧安全区）→ 任意可视高度都不裁；幂等（每次 Open 重设同一规范值） |
| 说明 | 仅动 `CharacterDockForm` 运行时布局（`ApplyResponsiveLayout/RepinTopCenter`），不重生成预制体、不动其它 UI |

### 可在编辑器配置（升级为配置驱动，无需改代码）

`SidePanelForm`（CharacterDockForm 的基类组件，选 CharacterDockForm.prefab 的该组件即可）新增序列化配置：

| Inspector 字段 | 含义 |
|---|---|
| `Slide Direction` | 决定面板**从哪个方向滑入、朝哪个方向滑出隐藏**：Right/Left/Top/Bottom |
| `Fill Canvas` | 勾选=展开时铺满整块画布并沿方向滑出（默认）；**不勾选=完全遵循预制体里调好的面板矩形（位置+尺寸都不移动）**，仅方向决定滑入/滑出路径 |
| `Panel Size` | 仅 Fill Canvas=未勾选 时可选：用来覆盖预制体尺寸——左右方向填 x=宽度、上下方向填 y=高度；**填 0 = 不改，遵循预制体原尺寸** |
| `Hidden Margin` | 收起时再滑出屏幕的额外余量 |
| 说明 | 非占满时几何保持预制体原样（实测：anchoredPosition 保持 -433.37、宽 1486.63 不变）；隐藏位移按“当前面板位置完全推出画布”动态计算（GetHiddenPos/ComputeClearShift），Left=向左滑出(-1950,0) 等均验证正确 |

- 几何在 `OnInit` 与每次 `OnOpen` 都按配置重摆（`ApplyConfigLayout`），池化复用/运行中改配置即时生效；
- 收起位移仍按当前面板实际尺寸+余量动态计算，方向改后滑出/滑入方向自动正确；
- 该组件字段已随预制体序列化（编辑器可直接改并保存），工程脚本**不会重生成该预制体**、不覆盖你的设置；
